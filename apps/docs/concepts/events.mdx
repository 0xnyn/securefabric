---
title: "Events"
description: "What SecureFabric tells you about, and the two ways to receive it: webhooks or the event feed."
---

SecureFabric records an event when something you may need to react to happens: a connection is created, a sync finishes, a connection's health changes, an action completes. An event is recorded in the same transaction as the change it describes, so an event exists if and only if the change happened.

## Receive events

<CardGroup cols={2}>
  <Card title="Webhooks" icon="bell" href="/webhooks/setup">
    SecureFabric posts each event to your HTTPS endpoint, signed, with retries.
  </Card>
  <Card title="Event feed" icon="list" href="#pull-the-event-feed">
    Your backend reads events in order with `GET /v1/events`.
  </Card>
</CardGroup>

Both carry the same event objects.

## The event object

```json
{
  "id": "evt_0193b7c4d1e27a3f9b5c6d7e8f901234",
  "type": "sync.completed",
  "created_at": "2026-12-01T10:15:00.000Z",
  "environment_id": "0193b79d-…",
  "organization_id": "0193b79e-…",
  "connection_id": "0193b79f-…",
  "sequence": 4182,
  "data": {}
}
```

| Field | Meaning |
|---|---|
| `id` | Unique event ID, `evt_…`. Webhook retries carry the same ID: use it to deduplicate. |
| `type` | The event type. See [Event types](/webhooks/event-types). |
| `connection_id` | The connection the event concerns, or `null`. |
| `organization_id` | The connection's organization on sync and health events, otherwise `null`. |
| `sequence` | Increases with every event of the same connection, in the order the changes happened. Use it to order events of one connection. |
| `data` | The type-specific payload. |

## Pull the event feed

```bash
curl "https://api.securefabric.dev/v1/events?type=sync.completed&limit=100" \
  -H "Authorization: Bearer $SF_API_KEY"
```

| Parameter | Meaning |
|---|---|
| `after` | Return events after this event ID. Pass the previous response's `next_cursor`. |
| `type` | Comma-separated event types. |
| `connectionId` | Only events of this connection. |
| `limit` | Events per page. |

Events come back in ID order. Store the last `next_cursor` and pass it as `after` on your next poll. Events are kept for 90 days. Requires the `data:read` scope.

<Note>
  The feed suits backends that can't receive webhooks. If you need every event, prefer webhooks, which retry each delivery: an event committed slightly late can carry an ID lower than one you already read.
</Note>
